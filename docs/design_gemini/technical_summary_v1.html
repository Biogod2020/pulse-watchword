1. 一页结论

系统定位：Pulse 是一个能够常态化被动运行（一直在看、一直在听）的多模态实时 Agent，核心原则是“判断用 djev、执行用大模型”，即绝大多数常规音画帧由毫秒级极小模型完成是否/选择过滤，仅在极少数产生状态迁移或用户交互时才唤醒高耗时大语言模型，并完全避免存储视频和原始音频。

✅ 已实现核心
  • Heartbeat 事件循环与重试调度
  • 版本化工作记忆与版本失效机制
  • djev 毫秒级原生判断（文本/图）
  • 工具循环执行（支持直接返回）
  • 双模态隔离向量检索
  • 日常场景离线回放（12 事件）
🟡 部分实现
  • 记忆系统（四层逻辑全在内存）
  • 调度优先级与队列事件合并
  • Model 提供方接入（验证了 luna）
  • 评测体系（仅完成 30 句文本集）
⬜ 待做事项
  • 输入层（浏览器摄像头/ASR）
  • 画面前后端双重去重过滤
  • 三栏 Web 界面与实时 WebSocket
  • SQLite + 向量持久化落盘
  • 大模型输出证据框坐标
  • Muse 模型适配与实拍评测
接下来三天的核心突破重点：
  1. 打通端到端输入与界面通路：实现浏览器端摄像头采集（640px/1fps）、灰度差分过滤及 WebSocket 双向通信，上线三栏监控页面，使离线回放逻辑变为可见、可交互的活系统。
  2. 切换并校准生产模型（Muse）：验证 muse-spark-1.3-contributor 的工具调用、视觉看图能力，攻克结构化目标边界框输出，替换开发期代理模型。
  3. 落地基础存储并录制演示视频：将内存工作记忆与情景表结构迁移到基础 SQLite，准备固定走位与实拍素材，录屏留存兜底演示。

3. 核心专项：判断题设计实验

系统能否在被动感知下节约成本，全依赖 djev 的“直觉门禁”。在包含 30 句带陷阱文本的离线测试集上，团队对比了 5 种不同的判断题架构：

设计方案 读取次数 耗时 p50 误判数 (致错动作) 结论与成因剖析
1. 最初合并式设计 单次 - 8 处 淘汰。多意图掺杂在一起，模型无法精准解耦边界。
2. 6 个原子问题一次读取 单次 - 12 处 淘汰。宽泛门控题（如“是否关于纱布”）漏检严重（10/16 漏判）。
3. 分层判断机制 44 次 109 ms 4 处 备用。虽解耦了分类，但多次往返调用导致延迟与请求量骤增。
4. 5 个具体入口问题一次读取 单次 52 ms 3 处 过渡方案。避免了宽泛门控，误判集中在助手意图模糊边界。
5. 5 个具体问题 + 助手阈值0.8 (最终采用) 单次 52 ms 1 处 正式采用。原生 noul 是/否题，固定前缀锁定意图，结合专用阈值表现最优。
工程准则落地：原生是/否题（noul）必须配合严格锁定主语的固定前缀（如 "Does this utterance itself..." / "Does this image itself show..."），并在窄问题中明确写明排除项；弃用宽泛门控，全部使用各功能包的具体触发题。

4. 核心专项：存储容量评估（“存储会不会撑爆”）

Pulse 坚持“不存视频、不存录音、只存文字转写与关键帧”的原则。系统设计了严格的四层记忆生命周期机制：

层级 存储内容 生命周期与策略 预估容量占用
L0 感官缓冲 最近 60 秒原始高频画面与连续语音分段 内存循环覆盖，纯瞬时态，绝对不落盘 仅占用少量运行内存（<50 MB）
L1 情景记忆 通过去重过滤的关键帧缩略图、文字描述、向量索引 滚动保存 14 天，到达 14 天硬上限后仅留文字向量 约 20 MB/天，约 600 MB/月（硬上限 1 GB）
L2 证据帧 被具体事实引用（如“钥匙最后位置”）的高清原帧 受版本绑定，随对应事实失效而被覆盖替换 维持在数十张级别（约 5~15 MB）
L3 语义记忆 结构化文字事实、任务、每日摘要、语义向量 长期保留，夜间整理把当天情景压成文本摘要 极小（纯文本+256维向量，约 1~2 MB/月）
现状警告：当前代码库中全部四层记忆均常驻 Python 内存（未持久化）。上述 SQLite 表定义、文件按 SHA-256 存盘、14 天滚动清理和手动压缩命令纯属既定设计，尚未编码实现。若当前进程崩溃，所有状态即刻丢失。

5. 系统分层模块实现

5.1 输入层（浏览器端）

⬜ 待做
作用通俗解：在用户浏览器采集眼睛（画面）和耳朵（声音），经过初筛后发送给后端。
技术实现：调用 navigator.mediaDevices.getUserMedia 捕获视频流，Canvas 每秒抽取 1 帧缩放至 640px；语音调用浏览器 Web Speech API 输出分句文本（备用已有的赛前本地流式 ASR）；建立单条 WebSocket 连接，统一按契约格式 {kind, t, seg_id, rev, text | image} 向上推送事件并接收服务端回调；内置“暂停/删除最近 N 分钟”的隐私开关。
实测数据：尚无（尚未接入）。
下一步：实现浏览器前端页面，完成摄像头抽帧与 WebSocket 握手联调。

5.2 事件与运行循环 (Heartbeat)

✅ 核心已实现 🟡 调度部分实现
作用通俗解：系统的中枢神经节拍器，每一个输入事件触发一次完整的决策流程。
技术实现：在 pulse/heartbeat.py 中定义：
1. Heartbeat.on_event(ev: Event) 执行严格 8 步编排：① perceive 钩子 ② 写入工作记忆（语音修订使旧事实失效）③ 聚合静态与动态 Question，单次并发批量调 decide ④ 阈值分流 ⑤ 并发触发 Capability 及重试任务 ⑥ 确定性 Rule 兜底产生 Alert ⑦ remember 异步长期存储（失败静默）⑧ 组装 Tick 追踪轨迹。
2. 健壮性：重试以 pending.* 事实入工作记忆，上限 3 次，输入版本修订时立即丢弃；判断器异常时规则保障兜底。
实测数据：日常场景回放（包含任务/找物/销账/回答 12 个事件）验证完全正确。
下一步：实现高频图像关键帧合并队列；赋予语音提问高优先级；将长期记忆彻底剥离出主 Tick 循环至后台线程。

5.3 画面感知

🟡 部分实现
作用通俗解：提取画面的第一印象，看图回答“是什么”、“在干什么”。
技术实现：在 pulse/packs/daily.py 中通过 perceive 钩子调用 djev 原始生成接口 /v1/raw/chat/completions 输出一句话描述；使用 DjevDecider 对图像调用 noul 或带选项 choice 的是/否判断。注意：djev 的 span 接口仅能摘录文本，生成描述必须走生成接口。
实测数据：djev 带图是/否题耗时约 0.2 秒；画面写描述耗时 0.3~1.0 秒（首次预热约 15 秒）；4 帧合成画面（放下物品、物品种类、浇花动作）判定全对。
下一步：在前端实现灰度缩略图像素差、在后端补充向量相似度 >0.95 判定，补全这两处尚未实现的去重过滤器。

5.4 判断题设计（Heartbeat的“直觉”）

✅ 已实现
作用通俗解：给毫秒级小模型设计的提问结构，决定什么时候该打扰大模型。
技术实现：采用 Question(kind='noul')，以固定句式 "Does this utterance itself..." 锁定输入原文；各功能提供 dynamic(wm) 方法从待办事项抽取额外题目（如给每个任务动态下发“画面里是否有人在做这件事？”）；单次读取请求限制在 10 题以内，防止破坏 djev 输出格式。
实测数据：单张 H100 GPU 上 5~6 题并发读取耗时 50~110 ms；30 句标注集测试下，单层 5 个具体问题（助手阈值0.8）实现误判仅 1 处，p50 为 52 ms。
下一步：为题库增加哈希版本锁定校验；收集真实走位视频抽帧再次校准置信阈值。

5.5 模型提供方 (Model 角色)

🟡 部分实现
作用通俗解：充当系统的大脑思考者，负责复杂任务规划、写回答与调用工具。
技术实现：在 pulse/providers.py 中定义统一 OpenAICompatAgent.run(system, user, tools, max_steps=4, stop_after_tools=False)；支持 stop_after_tools 单步执行机制，针对记录类操作在工具执行后立刻断开，省去一次冗余推理往返；支持环境变量 PULSE_MODEL_BASE_URL / PULSE_MODEL / PULSE_MODEL_KEY_FILE 单点热切。
实测数据：开发替身 DeepSeek v4.1 每次需 2~8 秒（免费配额易触碰 429）；gpt-6-luna 测得工具调用 2.3 秒、看图 8.9 秒（不支持 /v1/decisions 原生判断接口）。
下一步：实现返回目标检测框坐标的结构化输出；在正式环境 muse-spark-1.3-contributor 上完成工具调用与识图能力验证。

5.6 工具层

🟡 部分实现
作用通俗解：大脑使用的手和脚，修改任务列表、记录物品、查询记忆。
技术实现：封装 Tool(name, description, parameters, handler)；内置核心工具集：add_task、update_task、list_open_tasks、item_locations、search_memory；所有写入逻辑严格执行版本隔离，提交前验证版本依赖，过期事实自动作废。
实测数据：离线任务新增、改期、物品查询调用均顺利通过。
下一步：（可选）通过官方 Python MCP 客户端接入 Google Calendar MCP 服务。

5.7 记忆与存储

🟡 部分实现 (全在内存)
作用通俗解：存放此刻所见（工作记忆）以及历史发生过的事（长期记忆）。
技术实现：pulse/memory.py 管理分段 Segment、证据 Evidence 和事实 Fact；add_segment 会在语音被修订时联动废除引用它的旧事实；pulse/longterm.py 通过 RemoteEmbedder 请求本地 EmbeddingGemma 2 服务（POST /embed，float32，768 维）；检索设计了双模态分开排名策略，语音与图像各自取 top-k 再归并，彻底解决了文字对文字天然相似度虚高挤占图像的模态偏差问题。
实测数据：nodecw1 CPU 上图嵌入需 2.0~2.6 秒；“glasses”与“my keys”跨模态检索均准确排在首位。
下一步：将内存对象映射至 SQLite 表结构（segments/frames/facts/evidence/episodes/tasks）；集成 256 维压缩向量。

5.8 功能包 (Packs)

✅ 已实现
作用通俗解：装卸不同场景业务逻辑的插件盒，切换场景只需替换包配置。
技术实现：一个包定义包含：判断题定义、dynamic 题目生成、触发执行的 Capability、Rule 兜底规则以及 perceive/remember 钩子。日常包 pulse/packs/daily.py 涵盖任务语音增改、物品视觉定点、动态做完销账、提问检索；并留有 pulse/packs/surgical_count.py（纱条清点）作为规范参考。
实测数据：在 12 个事件日常合成场景中，完整跑通语音建任务、改期、识别三件物品位置、看到浇花后动态销账全流程。
下一步：保持日常包稳定，实测后调整 task_seen 等判断阈值。

5.9 网页界面

⬜ 待做
作用通俗解：向评委和用户直观证明“AI一直在看、但极少打扰模型”的展示屏幕。
技术实现：采用 FastAPI + 纯静态三栏页面设计。左栏：视频实时画面与 ASR 滚动字幕；中栏：Heartbeat 实时节拍信息流，展示每一跳的题目、概率柱、模型唤醒状态与累计“总事件 N / 唤醒 M 次”节约计数器；右栏：任务清单、物品卡片（附带证据关键帧与红框）及记忆占用统计。
实测数据：尚无。
下一步：编写单文件静态页面，接入下行 WebSocket 协议（tick/memory/answer 事件）。

5.10 评测与可观测

🟡 部分实现
作用通俗解：黑匣子监控仪，每一次感知和判断都在后台留下可回溯记录。
技术实现：Heartbeat 每个 tick 均结构化沉淀完整轨迹 JSON（包含单项耗时、提问列表、置信概率、触发模型标志、状态变动）；eval_triggers.py 支撑对 trigger_labels.json 离线标注批量评估；提供 run_scenario.py 回归测试套件。
实测数据：已纳入 30 句文字回归集及 5 项离线集成测试。
下一步：制作包含实拍动作的视觉评测标注集。

5.11 部署与合规

🟡 框架就绪 / 联调中
作用通俗解：模型运行的算力拓扑与黑客松比赛规则防线。
技术实现：
1. 部署架构：djev 部署于 gpucw1 GPU0（vLLM 0.32、AWQ INT4 精度、FP8 KV Cache，单请求限 1 张图）；嵌入服务 embed_server.py 部署在 nodecw1 CPU（规划迁往 GPU 提速）；主应用驻留 headcw，通过 SSH 隧道端口打通。
2. 比赛合规：严格划分边界，赛期新编写 Pulse 全部代码（~1,500 行）、界面及 Muse 配置；复用赛前已有资产 djev 服务及基础模型权重；微调/评估素材严格限定本人合成及授权录制数据。
实测数据：离线环境已贯通隧道交互；预先录制视频作为防翻车兜底方案。
下一步：完成 headcw 与 gpucw1 的联调验证，将嵌入服务迁至 GPU。

6. 风险与待验证事项

⚠️ 核心风险警示
  • 生产模型 Muse 能力未知：开发期使用 gpt-6-luna 验证，正式切换到 muse-spark-1.3-contributor 后，其工具调用稳定性、看图能力及结构化目标框输出均未经过实测。
  • CPU 嵌入计算瓶颈：EmbeddingGemma 2 当前在 nodecw1 的 CPU 上运行，单图耗时高达 2~2.6 秒，若不尽快迁移到 GPU，无法承接实时处理。
  • 全内存崩溃即丢：存储系统未落盘，演示过程中一旦进程遭遇意外崩溃，状态与记忆将全部丢失。
🧪 实测关键待验证
  • 真实物理走位评测：当前视觉评测数据全部基于 4 帧合成画面，未经历真实光照形变、复杂背景与移动抖动的真实考验。
  • 前后端链路吞吐：浏览器 Web Speech API 在真实环境下的连续修订延迟，以及灰度像素差过滤能否有效压降 60% 以上的无用上行。
  • djev 首次预热延迟：实测初次生成描述存在长达 15 秒的模型冷启动，演示前必须执行脚本热身。
